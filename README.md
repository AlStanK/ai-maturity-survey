# Індекс ШІ-зрілості організаційної культури

Анонімне опитування культурної готовності компаній до системного використання
штучного інтелекту. Інструмент збору даних для кваліфікаційної роботи
програми SE MBA (Бізнес-школа МІМ-Київ).

**Стек:** статична сторінка на GitHub Pages → PostgreSQL (Supabase) → Metabase.

---

## Що всередині

| Файл | Призначення |
|---|---|
| `index.html` | Уся анкета: 47 питань, 10 кроків, розрахунок індексів. Самодостатній файл — стилі й логіка вбудовані, ззовні тягнуться лише вебшрифти Google. |
| `db/schema.sql` | Схема Postgres: таблиці, RLS-політики, представлення для аналітики. |
| `db/pgvector.sql` | Необов'язкове: семантичний аналіз відкритих відповідей через pgvector. |

Дизайн — система **AInoia**: токени кольору, типографіки, простору та ефектів
вбудовані у сторінку.

## Розгортання

### 1. База даних

Створити проєкт у [Supabase](https://supabase.com) (безкоштовного тарифу
вистачає), відкрити **SQL Editor** і виконати `db/schema.sql`.

Скрипт ідемпотентний — його можна запускати повторно.

Що він створює:

* `public.responses` — відповіді. Ключові поля винесені в колонки для зручних
  розрізів, повний набір лежить у `jsonb`.
* `public.report_subscribers` — email тих, хто хоче отримати звіт. **Окрема
  таблиця**, не пов'язана з відповідями.
* `v_company_summary` — агрегат по компанії, показує компанію лише за наявності
  **щонайменше 5 анкет**.
* `v_industry_benchmark` — галузевий бенчмарк без назв компаній.
* `v_process_gaps` — розриви «потрібно мінус зараз» по восьми процесах.

### 2. Підключення сторінки

У `index.html` знайти блок конфігурації на початку скрипта й заповнити:

```js
const SUPABASE_URL = "https://xxxxxxxx.supabase.co";
const SUPABASE_ANON_KEY = "eyJhbGci...";
```

Обидва значення — з розділу **Project Settings → API**.

Поки поля порожні, сторінка працює в локальному режимі: відповіді лишаються
в браузері респондента, індекси рахуються на пристрої, є кнопка вивантаження JSON.

### 3. Публікація

**Settings → Pages → Source: Deploy from a branch → `main` / root.**

Через хвилину сторінка буде доступна за адресою
`https://<user>.github.io/ai-maturity-survey/`.

### 4. Семантичний аналіз відкритих відповідей (необов'язково)

Питання 44 і 45 — вільний текст. Щоб працювати з ними не вручну, а групувати
за змістом, виконайте `db/pgvector.sql`. Він створює:

* `answer_embeddings` — вектори відповідей, індекс HNSW за косинусною відстанню;
* `similar_answers(embedding, field, limit)` — пошук близьких за змістом висловлювань;
* `v_pending_embeddings` — черга відповідей, які ще не оброблені.

Розмірність `vector(1536)` розрахована на `text-embedding-3-small`. Інша модель —
інша розмірність, типи `vector(n)` між собою несумісні.

Ембединги рахує окремий скрипт під власником бази. **З браузера це робити не можна:**
ключ моделі опинився б у коді сторінки.

> **Питання етики.** Відправка відкритих відповідей у зовнішній API ембедингів —
> це передача дослідницьких даних третій стороні. Перед цим варто або отримати
> згоду в тексті анкети, або рахувати ембединги локальною моделлю.

### 5. Metabase

Підключити як звичайну базу Postgres — дані з **Project Settings → Database**.
Metabase заходить під власником бази, тому бачить і таблиці, і представлення.

Почати варто з `v_company_summary` та `v_industry_benchmark`: обидва вже
враховують поріг анонімності.

## Чому потрібен HTTP-шар

Статична сторінка не може звертатися до Postgres напряму: Postgres спілкується
власним протоколом поверх TCP, а браузер так не вміє. Між ними завжди щось стоїть.

| Варіант | Що дає | Чого коштує |
|---|---|---|
| **Supabase** | Postgres + HTTP-API (PostgREST) + RLS з коробки. pgvector уже вбудований | Залежність від вендора |
| **Neon + Cloudflare Worker** | Керований Postgres, HTTP-шар — власні ~30 рядків коду | Дві служби замість однієї |
| **Власний Postgres + PostgREST** | Повний контроль, дані на своєму сервері | Потрібен сервер і його обслуговування |

Схема в `db/schema.sql` працює однаково в усіх трьох випадках — змінюється лише те,
куди `index.html` надсилає `POST`.

## Модель доступу

Анонімний ключ Supabase **публічний за задумом** — він лежить у коді сторінки,
який бачить кожен відвідувач. Безпеку тримають політики RLS:

* `anon` має право **тільки на INSERT**;
* `SELECT`, `UPDATE`, `DELETE` для `anon` не надані — жодної політики немає;
* права на представлення для `anon` відкликані окремо, бо представлення
  в Postgres виконуються з правами власника й інакше обходили б RLS.

Читати дані можна лише прямим підключенням до Postgres або ключем `service_role`.
**`service_role` ніколи не потрапляє у фронтенд.**

Перевірено на локальному Postgres 17 з pgvector: `anon` успішно додає рядок
і отримує `permission denied` на будь-яку спробу читання таблиці, представлення
чи таблиці ембедингів. Видалення відповіді каскадом прибирає її ембединги.

## Етика дослідження

* Ім'я, посада, IP-адреса респондента не збираються.
* Назва компанії потрібна для агрегації в межах організації; індивідуальні
  відповіді роботодавцю не передаються.
* Компанійний звіт формується лише за наявності **≥ 5 анкет**; цей поріг
  вбудований у представлення, а не тільки в регламент.
* Email для розсилки звіту зберігається в окремій таблиці й не потрапляє
  в `answers`.
* У тексті дослідження компанії не порівнюються й не ранжуються.

## Розрахунки

Зворотні пункти (`ps3`, `ps5`, `ps7`, `gv4`) інвертуються за формулою `6 − бал`.

| Індекс | Пункти |
|---|---|
| Психологічна безпека | `ps1`–`ps7`, адаптована шкала А. Едмондсон (1999) |
| Лідерство та правила | `gv1`–`gv8` |
| Сприйнята ефективність | `ef1`–`ef4`: операційний, управлінський, адаптивний вимір + якість |

Розрив по процесу = «потрібно» − «зараз». Відповіді «Н/З» виключаються
із середніх, а не рахуються нулем.
